## 一、为什么要做这次选型

S3-a 已交付「能看到 → 能表态 → 能把判断写成草稿送回对话（人确认）」。
S3-b 要回答的是**下一步怎么把「表态」变成「真正改变产出的动作」**，同时不踩自动化的坑。

---

## 二、公开生态实据（调研结果）

| 项目 | 版本 | 形态 | 关键点 |
|---|---|---|---|
| `dsh-annotate-sync` | 2.0.0 | **批注整批作为一条结构化消息进入当前对话** + `read_annotations` 按 selector 改源码 | 与我们最接近的形态：攒批 → 一条消息 → Agent 按批注改 |
| `dsh-image-annotate` | 0.7.1 | 框选 + 冻结帧 → 一条消息 | 图片维度的框选是明确需求 |
| `dsh-annotate` | 0.1.15 | UI 点选 → 结构化块 | 轻量，偏 UI 批注 |
| `dsh-output-gallery` | 0.10.0 | pin +「只看交付物」过滤 + 版本历史 | **表态层，比我们早约两个月** |

**结论**：外部生态里「框选批注 → 结构化消息 → 人确认 → Agent 改文件」已是成熟形态，
而我们当前的反馈篮缺的是**图片/视频的框选定位**（现在的判定只有卡片级，没有空间坐标）。

## 三、两个候选方案

### 方案 A（推荐）：框选批注 → 一条结构化消息 → 人确认 → Agent 改文件

**做什么**
- 在查看器里加框选 / 箭头 / 文字标注层，标注带**归一化坐标**（相对图片宽高的 0–1）
- 一条标注可以落在任意资产（图片 / 视频某帧 / 文件某行）
- 攒批后仍走现有「决策草稿」通道：生成一条结构化消息，**写进 composer，人确认后手动发送**
- Agent 侧通过既有 seam 读取结构化批注，按 selector 定位修改

**为什么优先**
| 维度 | 评价 |
|---|---|
| 风险 | **低** —— 仍然是人确认后发送，零自动发送，与 S3-a 的约束完全一致 |
| 游客感知 | **强** —— 「我圈出这里不对」比「这张卡我不满意」精确得多，一眼能懂 |
| 复用度 | 高 —— 复用现有反馈篮、决策草稿渲染、seam、原子写，只加标注层与坐标模型 |
| 生态验证 | 已有多项目验证该形态可行（`dsh-annotate-sync` / `dsh-image-annotate`） |

**代价**：需要新增标注层 UI（canvas 或 SVG 叠加）、坐标契约（要写进 `shared/protocol.js`）、
以及「标注 → 消息文本」的渲染逻辑。工作量中等。

### 方案 B（不推荐现在做）：L2 自动 steer / L3 cancel

**做什么**：插件直接向正在跑的 Agent 注入指令或调用 cancel，实时改变任务走向。

**为什么不优先**
| 维度 | 评价 |
|---|---|
| 风险 | **高** —— 需要触碰会话控制通道；我们已实证 `conversation.input` 在 boot 阶段未就绪，声明式 inject 会让宿主播废（v0.13.1 教训） |
| 可控性 | 差 —— 自动 steer 是**无人确认**的动作，与「人工闸门」的设计立场冲突 |
| 游客感知 | 其实弱 —— 用户很难判断"是我让它改的，还是它自己跑偏了" |
| 依赖 | 需要更高频的宿主私有 API 探测，宿主升级即碎 |

**处置**：L2 / L3 继续放**独立包 `dsh-gallery-decision`**，默认关闭，不进主包。
主包保持「零自动发送」的清晰立场。

---

## 四、选型结论

**S3-b 采用方案 A：框选批注 → 一条结构化消息 → 人确认 → Agent 改文件。**

理由排序：
1. **与既有设计立场一致**（人工确认闸门，不自动改变运行中的任务）
2. **游客感知最强**（空间定位比卡片级判定精确）
3. **复用成本最低**（反馈篮 / 草稿渲染 / seam / 原子写全部可复用）
4. 生态已有多个先例验证形态可行

**明确不做**：S3-b 不包含自动 steer、不包含 cancel。这两项归 `dsh-gallery-decision`，默认关。
